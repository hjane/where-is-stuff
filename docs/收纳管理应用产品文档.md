# 收纳管理应用产品文档

## 1. 产品概述

### 1.1 产品名称
**收纳助手 (Storage Assistant)**

### 1.2 产品定位
一款基于AI图像识别技术的智能收纳管理应用，帮助用户通过拍照识别物品并建立数字化收纳档案，支持语音查询物品位置，解决"东西找不到"的日常痛点。

### 1.3 核心功能
- **房间管理**：创建和管理多个房间（客厅、卧室、厨房等）
- **家具管理**：添加各类收纳家具（抽屉柜、衣柜、储物箱等）
- **AI图像识别**：上传物品照片，自动识别物品名称和类别
- **语音查询**：通过语音快速查询物品存放位置
- **会员系统**：区分免费/付费会员功能权限

### 1.4 目标用户
- 家庭收纳整理爱好者
- 经常找不到物品的普通用户
- 需要管理大量物品的小户型住户
- 搬家整理需求的用户

## 2. 页面结构设计

### 2.1 页面导航架构

```
┌─────────────────────────────────────────────────────────────┐
│                        底部导航栏                            │
├──────────────────────┬──────────────────────┬───────────────┤
│      🏠 首页          │      📦 房间         │      👤 我的   │
└──────────────────────┴──────────────────────┴───────────────┘

说明：
- 首页已有快捷添加入口，底部导航不需要单独的"添加"按钮
- 房间页面采用Tab式设计，左右滑动切换房间
- 减少页面嵌套，用户可快速抵达目标
```

### 2.3 页面详细设计

#### P01 首页
**布局结构：**
```
┌─────────────────────────────┐
│  🔍 搜索物品...         [🎤] │  ← 搜索栏+语音按钮
├─────────────────────────────┤
│                             │
│        🎤 大语音按钮         │  ← 核心：语音找物品
│     "说说话，帮你找东西~"     │
│                             │
├─────────────────────────────┤
│  录入入口                     │  ← 次要：录入物品
│  [📷 拍照录入] [🎤 语音录入]  │
├─────────────────────────────┤
│  我的收纳                     │  ← 物品统计概览
│  ┌────────┬────────┬────────┐│
│  │  5     │  12    │  156   ││
│  │ 房间   │ 家具   │ 物品   ││
│  └────────┴────────┴────────┘│
└─────────────────────────────┘
```

**设计说明：**
- **视觉层级**：搜索 > 录入 > 统计信息
- 搜索是最高频功能，放在最顶部和最显眼位置
- 录入是次要功能，放在中间区域
- 底部展示用户收纳统计（房间数、家具数、物品数），让用户一眼看到自己的收纳成果
- 统计数据实时计算，点击可跳转到对应页面
- 页面保持简洁留白，不堆砌辅助信息

**交互说明：**
- 点击大语音按钮：启动语音识别找物品
- 搜索栏：手动输入搜索
- 拍照录入：进入拍照流程（可先拍后选位置）
- 语音录入：进入语音收纳流程
- 点击统计数字：跳转到对应页面（房间数→P02，家具数→P02，物品数→搜索）

- 支持重命名：长按选择重命名
- 支持排序：拖拽≡图标调整顺序（从上到下）
- 删除后不可恢复，建议先移动重要物品

**底部弹窗操作：**
- 拍照更新：重新拍照识别，更新该空间物品（合并去重）
- 语音添加：语音录入新物品
- 清空空间：清空所有物品（会员功能）
- 删除原图：删除该空间的原始拍照图（释放存储空间）

#### P04 图片识别（支持两种流程）

**流程A：先选位置 → 再拍照（传统）**
```
选房间 → 选家具 → 选收纳空间 → 拍照 → 识别
```

**流程B：先拍照 → 再选位置（推荐，更便捷）**
```
拍照 → 选择位置 → 识别
```

**流程B详细步骤：**

**Step 1: 拍照**
```
┌─────────────────────────────┐
│  ← 拍照录入                 │
├─────────────────────────────┤
│  💡 对准整个抽屉拍照         │
│  每个空间最多N条识别记录     │
│  （免费1条/会员5条）         │
├─────────────────────────────┤
│  ┌─────────────────────┐    │
│  │                     │    │
│  │   📷 点击拍照       │    │
│  │                     │    │
│  └─────────────────────┘    │
└─────────────────────────────┘
```

**Step 2: 选择位置（拍照后）**
```
┌─────────────────────────────┐
│  ← 选择收纳位置    [15积分] │
├─────────────────────────────┤
│  最近使用的家具（快捷选择）   │
│  ┌─────────────────────┐    │
│  │ 🛏️ 主卧-床头柜      │ ✓ │  ← 默认选中最近使用的
│  │ 📍 第1层抽屉        │   │     显示上次使用的空间
│  ├─────────────────────┤    │
│  │ 🚪 次卧-衣柜        │   │  ← 第2个最近使用
│  ├─────────────────────┤    │
│  │ 📚 书房-书架        │   │  ← 第3个最近使用
│  └─────────────────────┘    │
│  [❌ 都不是，手动选择]        │
├─────────────────────────────┤
│  选中的位置：                │
│  主卧 > 床头柜 > [选择空间▼] │
│                             │
│  可选空间：                  │
│  ○ 第1层抽屉  ○ 第2层抽屉   │
│  ○ 柜子                      │
├─────────────────────────────┤
│    [✓ 确认，开始识别]  已拍1张 │
└─────────────────────────────┘
```

**快捷选择逻辑：**
- 显示最近使用过的3个家具
- 默认选中最近使用的那一个
- 选中家具后，还需选择具体收纳空间
- 点击"都不是"进入手动选择流程

**手动选择流程：**
```
左右滑动选房间 → 点击进入选家具 → 点击进入选空间 → 确认
```

**Step 3: 识别结果处理**
- 创建识别任务，后台异步识别
- 识别完成后，**合并去重**：新结果 + 原有物品
- 不是替换，是追加合并
- 用户收到通知，可查看结果

```typescript
interface RecognitionRecord {

  // 状态管理
  status: 'pending' | 'processing' | 'completed' | 'failed' | 'deleted';
  // deleted: 软删除状态，定时任务清理已删除记录及其图片

  errorMessage?: string;
  createdAt: Date;
  updatedAt: Date;
  deletedAt?: Date;             // 软删除时间
}
```

**识别记录数量限制：**
- 每个收纳空间最多N条正常状态的识别记录
- 免费用户：最多1条
- 付费会员：最多5条
- 前端查询时只获取 `status != 'deleted'` 的记录
- 达到上限时：免费用户提示升级，付费用户可删除旧记录后添加新记录

**删除权限：**
- 免费用户：不能删除识别记录
- 付费会员：可以删除识别记录（软删除，status='deleted'）
- 软删除的记录在服务端保留一段时间后由定时任务清理

### 3.3 索引设计（TCB MongoDB）

由于采用嵌入文档设计，索引策略有所调整：

```javascript
// 用户表索引
db.user.createIndex({ phone: 1 }, { unique: true });

// 房间表索引
db.room.createIndex({ userId: 1, sortOrder: 1 });

// 家具表索引
db.furniture.createIndex({ userId: 1, roomId: 1 });
db.furniture.createIndex({ userId: 1, updatedAt: -1 });

// 物品搜索索引（使用MongoDB文本索引）
db.furniture.createIndex(
  { "spaces.items.name": "text" },
  { name: "item_name_text_index" }
);

// 搜索历史表索引
db.search_history.createIndex({ userId: 1, createdAt: -1 });
```

**索引设计说明：**
- Space和Item作为嵌入文档，不单独建表，通过父文档查询
- 使用MongoDB文本索引支持物品名称搜索
- 查询时先定位到Furniture，再遍历spaces数组找到目标item

### 4.6 原始图片管理

#### 4.6.1 设计理念

**原图存储在 RecognitionRecord 中**

| 场景 | 处理方式 |
|------|----------|
| **日常使用** | 粗放管理，只记录物品种类（如"数据线"、"笔"） |
| **精细查找** | 查看原始拍照图，从图片中获取更多信息 |

**为什么保留原图？**
- 用户可能突然想知道某支特定的笔在哪
- 原图可以提供更多细节（颜色、品牌、具体位置）
- 作为兜底方案，不占用主界面

**存储方式：**
- 原图存储在 RecognitionRecord.imageUrl 中，不在 Space 中
- 一个空间可以有多条识别记录，每条记录一张图片
- 用户查看原图时，通过 spaceId 查询 RecognitionRecord（status != 'deleted'）获取
- 支持软删除（status='deleted'），定时任务清理已删除记录及关联图片
- 免费用户最多1条记录，付费会员最多5条记录
- 免费用户不能删除记录，付费会员可以删除（软删除）

## 5. 会员与积分系统设计

### 5.1 设计原则

**核心思路：会员费 + 积分制**

| 收入来源 | 用途 | 说明 |
|----------|------|------|
| **会员订阅费** | 覆盖服务器、存储、基础功能成本 | 固定收入，保证基础运营 |

| **皮肤/图标** | 商业化扩展（后续） | 积分购买，增加用户粘性 |

- 积分制让轻度用户少花钱，重度用户多花钱
- 类似Notion AI、Midjourney的成功模式

```typescript
class PermissionService {
  // 检查是否可添加房间
  canAddRoom(user: User, currentCount: number): boolean {
    const limits = { free: 3, basic: 10, pro: Infinity };
    return currentCount < limits[user.membershipType];
  }

  // 检查积分是否足够
  hasEnoughCredits(user: User, required: number): boolean {
    return user.credits >= required;
  }

  // 消耗积分
  async consumeCredits(user: User, amount: number, feature: string): Promise<boolean> {
    if (user.credits < amount) {
      throw new Error('积分不足，请充值');
    }
    user.credits -= amount;
    await this.recordTransaction(user.id, -amount, feature);
    return true;
  }

  // 检查是否可一键清空（会员功能）
  canClearSpace(user: User): boolean {
    return user.membershipType !== 'free';
  }
}
```

## 9. 界面原型建议

### 9.1 设计原则

#### 核心设计理念

**物品 = 纯文本，家具/房间 = 美观图标**

| 元素 | 设计方式 | 原因 |
|------|----------|------|
| **物品** | 纯文本Tag（名词） | 粗放管理，只是一个分类名称，无需复杂设计 |
| **家具** | 精美图标/插画 | 视觉重点，可做皮肤商业化 |
| **房间** | 精美图标/插画 | 视觉重点，可做皮肤商业化 |

#### 设计原则详解

1. **物品设计：简洁文本**
   - 物品以Tag标签形式展示，就是一个名词
   - 例如："数据线"、"充电器"、"耳机"、"护照"
   - 不需要复杂的图标或图片
   - 特殊情况：书（显示书名）、衣服（显示"红色T恤"）

2. **家具设计：精美图标**
   - 每种家具有一套精美的图标
   - 可生成多套风格：卡通、简约、复古等
   - 作为皮肤商业化，用户可用积分购买
   - 图标要能体现家具特征（抽屉柜有抽屉，衣柜有门）

3. **房间设计：主题图标**
   - 房间以图标+名称展示
   - 可配合家具图标形成主题包
   - 例如：卧室主题、书房主题、厨房主题

4. **整体风格一致性**
   - 同一套皮肤内，房间、家具、UI元素风格统一
   - 物品Tag保持简洁，不随皮肤变化

## 11. 注意事项

### 11.1 图片识别优化
- 识别前对图片进行压缩，减少上传时间和API调用成本
- 设置置信度阈值（如80%），低于阈值的建议用户手动输入
- 支持批量识别，提升用户体验
- 建立物品名称词库，优化识别结果
- **采用异步识别方案**：用户上传后立即返回，后台处理识别任务，避免用户等待
- **任务状态管理**：使用TCB数据库记录识别任务状态，支持轮询查询或推送通知
- **失败重试机制**：云函数内部实现重试逻辑，单张图片失败不影响整体任务

### 11.2 性能优化
- 图片懒加载，优先加载缩略图
- 列表分页加载，避免一次性加载大量数据
- 本地缓存常用数据（房间、家具列表）
- 识别结果本地缓存，减少重复调用API

### 11.3 用户体验
- 添加操作引导（首次使用提示）
- 空状态设计（无房间/无物品时的引导）
- 操作反馈（Toast提示、加载状态）
- 错误处理（网络异常、识别失败）

### 11.4 数据安全
- 用户数据隔离，严格校验权限
- 图片存储使用私有bucket，通过签名URL访问
- 敏感操作（删除）需要二次确认
- 定期数据备份

### 11.5 TCB开发注意事项

#### 11.5.1 免费额度与计费
| 资源 | 免费额度 | 超出后计费 | 建议 |
|------|----------|------------|------|
| 云函数调用 | 100万次/月 | 0.0133元/万次 | 足够MVP阶段使用 |
| 云函数运行时间 | 40万GBs/月 | 0.00011108元/GBs | 注意优化函数执行时间 |
| 数据库存储 | 5GB | 0.07元/GB/天 | 图片URL存数据库，文件存Storage |
| 数据库读操作 | 5万次/天 | 0.05元/万次 | 合理使用索引，减少全表扫描 |
| 数据库写操作 | 5万次/天 | 0.25元/万次 | 批量写入，减少操作次数 |
| 存储容量 | 5GB | 0.0043元/GB/天 | 压缩图片，定期清理临时文件 |
| 存储下载流量 | 5GB/月 | 0.29元/GB | CDN加速，减少回源流量 |

#### 11.5.2 云函数限制
- **执行时间**：单次执行最长30秒（异步任务可拆分多个函数）
- **内存限制**：128MB - 16GB可选（识别任务建议512MB以上）
- **并发限制**：默认1000并发，可申请提升
- **代码包大小**：最大500MB（包含依赖）
- **环境变量**：最大4KB

#### 11.5.3 数据库设计建议
- 使用 `_openid` 字段自动关联用户，简化权限控制
- 合理使用索引，查询字段必须建立索引
- 避免单文档超过1MB
- 使用聚合查询减少多次读取

#### 11.5.4 图片处理优化
- 上传前客户端压缩图片（建议宽度1080px，质量80%）
- 使用TCB Storage的CDN加速访问
- 缩略图和原图分开存储，列表展示使用缩略图
- 设置合理的缓存策略

#### 11.5.5 离线支持
- 使用SQLite本地缓存，支持离线查看
- 离线操作队列，网络恢复后自动同步
- 数据冲突处理策略（服务端优先或客户端优先）

### 12.2 数据模型可扩展性设计

当前版本实现了粗放管理（Space.items 为字符串数组）。精细管理将在后续版本中开发，届时通过独立的物品类型表实现。

#### 12.2.1 扩展机制

**核心设计：** 精细管理时，Space.items 为空，物品存在独立的类型表中（如 clothing、food、book、shoe），通过 `furniture.itemType` 决定查哪张表。

**扩展新类型只需2步：**
1. 在 `FURNITURE_TYPE_CONFIGS` 中新增一个类型配置，设置 `managementMode: 'fine'` 和 `itemType`
2. 创建对应的数据库表（如 clothing 表）

无需修改核心数据模型。

#### 12.2.2 食物/冰箱收纳（近期可扩展）

**场景描述：** 将冰箱作为家具纳入收纳管理，记录冰箱内食物的存放位置和过期时间。

**扩展方式：** 在预定义家具类型中新增冰箱配置：
```typescript
{
  id: 'refrigerator',
  name: '冰箱',
  icon: '🧊',
  managementMode: 'fine',
  itemType: 'food',
  defaultSpaceType: 'shelf',
  defaultSpaceCount: 4,
  allowDynamicSpace: true
}
```

**需要新增的功能：**
- 创建 food 表（name, expiryDate, quantity, storageRequirement 等字段）
- 过期提醒：基于 food.expiryDate，到期前N天推送提醒
- 食物快速增减：冰箱物品变动频繁，需要更便捷的增删操作
- 数量管理：食物需要记录具体数量（不同于普通物品的去重策略）

#### 12.2.3 其他可扩展场景

| 场景 | 新增家具类型 | itemType | 独立表 |
|------|-------------|----------|--------|
| **药品管理** | medicine_cabinet | medicine | medicine 表 |
| **化妆品管理** | vanity | cosmetics | cosmetics 表 |
| **工具管理** | toolbox | tool | tool 表 |
| **文件管理** | file_cabinet | document | document 表 |

#### 12.2.4 可扩展性设计原则

1. **类型隔离**：每种精细家具类型有独立的物品表，互不干扰
2. **向后兼容**：新增类型不影响已有数据，旧版本可忽略未知字段
3. **零代码扩展**：新增家具类型只需添加配置和创建表，无需修改核心逻辑

### 12.3 精细管理设计思路（后续开发）

当前版本仅实现粗放管理（Space.items 为字符串数组）。精细管理将在后续版本中开发。

#### 12.3.1 核心思路

精细管理时，Space.items 为空，物品存在独立的类型表中：

| itemType | 表名 | 说明 | 示例字段 |
|----------|------|------|----------|
| clothing | clothing | 衣物 | name, color, type, brand, size |
| food | food | 食物 | name, expiryDate, quantity, storageRequirement |
| book | book | 书籍 | name, author, publisher, isbn |
| shoe | shoe | 鞋子 | name, color, type, brand |

#### 12.3.2 查询逻辑

```typescript
// 粗放管理：直接从 Space.items 获取
const items = space.items; // ["遥控器", "充电器"]

// 精细管理：根据 furniture.itemType 查对应表
if (furniture.managementMode === 'fine') {
  const tableName = furniture.itemType; // e.g., 'clothing'
  const items = await db.collection(tableName).where({ spaceId: space.id }).get();
}
```

#### 12.3.3 识别流程差异

- 粗放管理：AI识别 → 提取物品名称 → 存入 Space.items（字符串数组）
- 精细管理：AI识别 → 根据家具类型提取物品+属性 → 存入对应类型表

#### 12.3.4 详情页面差异

精细管理的家具详情页展示不同的界面：
- 衣柜：显示衣物列表（带颜色/类型标签）
- 书架：显示书籍列表（带作者信息）
- 冰箱：显示食物列表（带过期时间提醒）

粗放管理的家具详情页：显示物品Tag列表（纯文本）
